개념 01

점근적 표기법 — Big-O, Big-Ω, Big-Θ

세 표기법은 같은 대상(자원 소모량의 증가율)을 서로 다른 각도에서 봅니다.

표기의미실생활 비유
O(f(n))상한선 — 최악의 경우 이보다 느리지 않다"아무리 막혀도 30분 안에는 도착한다"
Ω(f(n))하한선 — 최선의 경우 이보다 빠르지 않다"아무리 뻥 뚫려도 10분보다 빨리는 못 간다"
Θ(f(n))상한=하한 — 사실상 정확한 증가율"매번 거의 정확히 15분 걸린다"

실무에서는 최악의 경우를 대비해야 하므로 O(f(n))가 압도적으로 자주 쓰입니다. 이 강좌에서 "복잡도"라고 말하면 특별한 언급이 없는 한 Big-O를 뜻합니다.

상황주로 쓰는 표기
"최악의 경우 얼마나 걸릴지 보장해야 한다" (실무 대부분)O
"이 문제는 최소 몇 번의 연산이 필요한지 증명한다" (알고리즘 이론)Ω
"최선·최악이 같아서 정확한 증가율을 말하고 싶다" (교재·논문)Θ

그렇다고 Ω와 Θ가 쓸모없는 건 아닙니다. Ω(하한)는 "이 문제는 아무리 잘 짜도 최소 이만큼은 걸린다"는 문제 자체의 한계를 증명할 때 씁니다 — 예를 들어 비교 기반 정렬은 Ω(N log N)이라는 사실은, 어떤 정렬 알고리즘을 만들어도 비교 연산만으로는 이보다 빠를 수 없다는 하한 증명입니다. 덕분에 엔지니어가 불가능한 최적화에 시간을 낭비하지 않게 됩니다.

🔎 그런데 "비교 기반 정렬은 Ω(N log N)"이라는 건 어떻게 증명할 수 있을까? — 결정 트리(Decision Tree) 논증

핵심 아이디어: 원소끼리 <, >로만 비교하는 정렬 알고리즘(퀵 정렬, 병합 정렬, 힙 정렬 등)의 실행 과정은 하나의 이진 결정 트리로 그릴 수 있습니다. 각 내부 노드는 "원소 A와 B를 비교한다"는 한 번의 비교이고, 그 결과(A<B 인지 A>B 인지)에 따라 왼쪽·오른쪽 가지로 내려갑니다. 각 리프(leaf)는 하나의 "정렬 결과(순열)"를 의미합니다.

  1. 리프의 개수: 원소가 N개면 가능한 순서(순열)는 N!가지입니다. 알고리즘이 이 N!가지를 전부 구별해내려면 트리에 최소 N!개의 리프가 있어야 합니다.
  2. 트리 높이 = 비교 횟수: 이진 트리는 높이가 h일 때 리프가 최대 2h개입니다. 따라서 2h ≥ N! 이 성립해야 하므로, h ≥ log₂(N!) 입니다. 여기서 h가 곧 "최악의 경우 필요한 비교 횟수"입니다.
  3. log₂(N!) 정리: 스털링 근사에 따르면 log₂(N!) ≈ N log₂N − N log₂e 이고, 최고차항만 남기면 log₂(N!) = Θ(N log N)입니다.

즉, 비교만 사용하는 정렬 알고리즘은 아무리 잘 설계해도 최소 Ω(N log N)번의 비교가 필요하다는 것이 수학적으로 증명됩니다. 그래서 병합 정렬·힙 정렬의 O(N log N)은 우연이 아니라 이미 이 하한선에 도달한 최적의 알고리즘이라는 뜻입니다. (참고: 계수 정렬·기수 정렬처럼 값을 비교하지 않고 다른 성질을 이용하는 정렬은 이 하한을 벗어나 O(N)도 가능합니다 — 이 증명은 어디까지나 "비교 기반" 정렬에 한정됩니다.)

Θ(상한=하한)는 최선·최악의 성능 차이가 거의 없는 알고리즘(예: 병합 정렬 — 항상 Θ(N log N))을 "입력과 무관하게 항상 이 정도 걸린다"고 정확히 표현하고 싶을 때 씁니다. 반대로 퀵 정렬처럼 최선(Θ(N log N))과 최악(Θ(N²))이 크게 갈리는 알고리즘은 Θ 하나로 뭉뚱그릴 수 없어서, 이럴 땐 오히려 O로 최악만 짚어 말하는 게 더 실용적입니다.

🔎 예측하기 — 아래 함수 mystery(n)의 시간 복잡도는 O(n²), O(n log n), O(n) 중 무엇일까요? 겉보기엔 이중 루프지만, i가 어떻게 변하는지 잘 보세요.
def mystery(n):
    count = 0
    i = 1
    while i < n:
        for j in range(i):
            count += 1
        i *= 2      # i가 두 배씩 늘어난다
    return count
n = n = 32

안쪽 루프가 도는 횟수(1, 2, 4, 8, …)를 막대 조각으로 이어 붙였습니다. 조각들의 합이 n 전체 길이에 얼마나 가까운지 확인해 보세요.

n

힌트: 바깥 루프가 도는 횟수와, 안쪽 루프가 매번 도는 횟수(1, 2, 4, 8, …)를 각각 세어 전체 반복 횟수의 합을 구해보세요.

정답은 O(n)입니다. i가 1, 2, 4, 8, …로 두 배씩 늘어나므로 바깥 루프는 log₂(n)번만 돕니다. 이때 안쪽 루프의 반복 횟수를 모두 더하면 등비수열의 합 공식에 의해 n의 2배 미만에 항상 머뭅니다(위 시각화에서 n이 2의 거듭제곱이 아닐 때는 합이 n보다 커질 수도 있다는 걸 직접 확인해 보세요). 정확한 값이 n보다 크든 작든 중요하지 않습니다 — n이 커져도 합이 n에 비례해서만 늘어난다는 사실 자체가 O(n)이라는 뜻입니다. 즉 "루프가 두 겹이니 무조건 O(n²)"이라는 성급한 결론은 틀렸습니다 — 안쪽 루프의 반복 횟수가 매번 달라질 때는, 각 반복마다 실제 실행 횟수를 더해서 총합을 구해야 정확한 복잡도가 나옵니다. 이런 패턴은 이후 힙(9주차)의 heapify 분석에서도 똑같이 등장합니다.

🔬 실습으로 직접 확인하기 — 정말 O(n)이 맞을까?

추론이 맞는지 실제로 실행시간을 재서 검증해 봅시다. n을 두 배씩 늘려가며 mystery(n)의 실행 시간을 측정하세요. O(n)이라면 n이 두 배가 될 때 시간도 대략 두 배가 되어야 합니다(O(n²)이라면 네 배, O(log n)이라면 거의 변화가 없어야겠죠).

import time

def mystery(n):
    count = 0
    i = 1
    while i < n:
        for j in range(i):
            count += 1
        i *= 2
    return count

def bench_mystery(n):
    start = time.perf_counter()
    mystery(n)
    return time.perf_counter() - start

for n in [100_000, 200_000, 400_000, 800_000, 1_600_000]:
    print(n, bench_mystery(n))

mystery(n) 실측 시간 — 직선에 가깝다면 O(n)이 맞다는 뜻
연습 · 개념 01 적용

코드만 보고 복잡도 예측하기

아래 네 가지 코드를 보고, 먼저 스스로 복잡도를 적어본 뒤 정답을 확인하세요. 정답만 맞히는 것보다 "왜 그런지" 근거를 한 문장으로 말할 수 있는지가 더 중요합니다.

연습 ① — 두 개의 순차적인 반복문

def f1(n):
    for i in range(n):
        print(i)
    for j in range(n):
        print(j)
🔎 이 함수의 시간 복잡도는? (O(n), O(n²), O(2n) 중 가장 정확한 표현은?)
정답은 O(n)입니다. 두 반복문이 중첩(nested)된 것이 아니라 순차적으로 실행되므로 연산 횟수는 n + n = 2n입니다. Big-O는 상수 배수를 무시하므로 O(2n)이 아니라 O(n)으로 씁니다. "반복문이 두 개 있다고 무조건 O(n²)"이라는 오해를 조심하세요 — 중첩되어 있는지, 나란히 있는지를 먼저 확인해야 합니다.

연습 ② — 안쪽 루프의 범위가 바깥 변수에 의존

def f2(n):
    count = 0
    for i in range(n):
        for j in range(i):
            count += 1
    return count
🔎 이 함수의 시간 복잡도는?
정답은 O(n²)입니다. 안쪽 루프가 매번 0, 1, 2, …, n-1번 돌므로 전체 반복 횟수는 0+1+2+…+(n-1) = n(n-1)/2 입니다. 최고차항만 남기고 계수와 낮은 차수 항을 버리면 O(n²)이 됩니다. 실습①에서 본 insert(0, x)를 n번 반복하는 것과 정확히 같은 형태입니다.

연습 ③ — 매번 절반씩 줄어드는 반복

def f3(n):
    count = 0
    while n > 1:
        n = n // 2
        count += 1
    return count
🔎 이 함수의 시간 복잡도는?
정답은 O(log n)입니다. n이 매 반복마다 절반이 되므로, n이 1 이하로 줄어들 때까지 걸리는 반복 횟수는 "n을 몇 번 2로 나눠야 1이 되는가", 즉 log₂(n)번입니다. 이 패턴은 이진 탐색(12주차)의 핵심 원리와 완전히 동일합니다.

연습 ④ — 반복문은 하나뿐인데 왜 O(n²)일까? (숨어있는 반복문 함정)

def contains_dup(nums):
    for i in range(len(nums)):
        if nums[i] in nums[i+1:]:
            return True
    return False
🔎 for문은 딱 하나뿐입니다. 그런데 정말 O(n)일까요? 힌트: 파이썬 리스트에서 x in lst(값이 들어있는지 검사)는 최악의 경우 리스트를 처음부터 끝까지 순차 비교하므로 그 자체로 O(N)입니다.
정답은 O(n²)입니다. for문이 한 겹이니 O(n)이라고 생각하기 쉽지만, 그 반복문 안에서 호출하는 nums[i] in nums[i+1:] 자체가 이미 리스트를 처음부터 끝까지 훑는 O(N) 연산입니다. 즉 코드에는 눈에 보이는 for문이 하나뿐이지만, 실제로는 "O(n) 루프 안에 O(n) 연산이 숨어있는" 이중 루프와 같은 구조입니다. 그래서 전체는 O(n) × O(n) = O(n²)이 됩니다. 함수나 연산자를 호출할 때 그 내부 복잡도까지 감안해야 정확한 분석이 됩니다 — 이후 6주차 해시 테이블에서 x in dict(O(1))로 바꾸면 왜 성능이 극적으로 개선되는지 이해하는 기초가 됩니다.

개념 02

메모리의 물리적 연속성 — "고정된 도서관 책장"

파이썬의 list는 내부적으로 연속된 메모리 블록에 원소의 참조를 순서대로 저장합니다. 이걸 도서관 책장에 비유하면 이렇습니다.

책장의 칸은 이미 못으로 고정되어 있습니다. 맨 끝 칸에 책을 추가하는 건 쉽습니다 — 바로 옆에 꽂으면 되니까요 (평균 O(1)). 하지만 맨 앞이나 중간에 책을 끼워 넣으려면, 그 뒤에 있는 책을 전부 한 칸씩 밀어야 합니다 (O(N)). 책장이 꽉 차면 관리인이 더 큰 새 책장을 통째로 구해와서 기존 책을 전부 옮겨 꽂습니다 — 이것이 동적 배열의 재할당(resize)입니다.

연산코드평균 복잡도왜?
끝에 추가lst.append(x)O(1) (분할상환)여유 공간이 있으면 바로 삽입
끝에 추가(재할당 순간)lst.append(x)O(N)더 큰 메모리 블록으로 전체 복사
맨 앞/중간 삽입lst.insert(0, x)O(N)뒤 원소를 전부 한 칸씩 이동
인덱스 접근lst[i]O(1)주소 계산만으로 즉시 위치 특정
값으로 검색x in lstO(N)처음부터 순차 비교

위 표의 두 줄 — "끝에 추가" O(1)과 "끝에 추가(재할당 순간)" O(N) — 은 서로 다른 걸 가리키는 게 아니라, 같은 append를 보는 두 가지 관점입니다. append 한 번만 딱 떼어놓고 볼 때, 그 호출이 우연히 재할당을 유발한다면 그 한 번은 O(N)이 걸립니다. 하지만 append를 여러 번 반복했을 때 평균을 내면, 재할당은 아주 가끔만 일어나므로 전체 평균은 O(1)에 가까워집니다 — 이것이 "평균 O(1) (분할상환)"이라는 표기의 의미입니다. 즉 O(N)은 "최악의 한 순간", O(1)은 "여러 번에 걸친 평균"을 말하는 것이므로 모순이 아닙니다. 아래 예측하기에서 이 관계를 숫자로 직접 확인해 보세요.

🔎 예측하기 — 아래 코드에서 append 100만 번 중, O(N)이 걸리는 재할당은 대략 몇 번 일어날까요?
lst = []
for i in range(1_000_000):
    lst.append(i)
동적 배열이 꽉 찰 때마다 용량을 이전의 k배로 늘린다고 하면, 크기 1에서 n까지 도달하는 데 필요한 재할당 횟수는 대략 logk(n)번입니다(매번 용량이 k배가 되니, n에 도달하려면 k를 그만큼 여러 번 곱해야 하기 때문입니다).
  • 단순히 "두 배씩 늘어난다"(k=2)고 가정하면 log₂(1,000,000) ≈ 20번입니다.
  • 하지만 CPython이 실제로 쓰는 성장 계수는 2배가 아니라 약 1.125배에 가깝습니다(완만하게 늘려서 메모리 낭비를 줄이기 위함). 이 경우 ln(1,000,000)/ln(1.125) ≈ 약 117번입니다.
어느 쪽 숫자를 쓰든 결론은 같습니다 — 100만 번의 append 중 재할당은 수십~백여 번, 즉 0.01% 수준밖에 일어나지 않습니다. 이렇게 극소수의 O(N) 이벤트를 전체 호출 수로 나누어 "평균"을 내면, append 한 번당 비용은 사실상 O(1)로 수렴합니다 — 이것이 분할상환(amortized) O(1)의 의미입니다.
개념 03

공간 복잡도(Space Complexity) — 시간 말고 메모리도 잰다

지금까지는 "얼마나 오래 걸리는가"(시간 복잡도)만 이야기했습니다. 하지만 이번 주 핵심 질문이 애초에 "얼마나 빠르며, 메모리를 얼마나 차지할지"였다는 걸 기억하시나요? 공간 복잡도는 입력 크기 n이 커질 때 알고리즘이 추가로 필요로 하는 메모리가 어떻게 늘어나는지를 시간 복잡도와 똑같이 Big-O로 표현한 것입니다.

상황공간 복잡도이번 주 예시
입력과 무관하게 변수 몇 개만 사용O(1)응용① hi, lo / 응용②의 in-place 수정 / 응용③의 left, right
입력 크기에 비례하는 새 리스트를 생성O(N)sorted(nums), 응용④에서 만드는 result
두 입력을 합친 만큼의 새 자료구조O(N+M)응용④ merge_sorted(a, b)
재귀 호출이 쌓아올리는 호출 스택O(호출 깊이)아직 다루지 않음 — 7주차 트리 재귀에서 본격적으로 등장

⚠️ 공간 복잡도를 따질 때 자주 놓치는 것들

  1. 입력 자체는 보통 세지 않는다(추가 공간 기준). "이 알고리즘의 공간 복잡도는 O(N)"이라고 할 때, 대개는 함수가 넘겨받은 입력 배열 자체가 아니라 그 외에 추가로 사용한 메모리만 셉니다. 입력까지 포함하면 거의 모든 알고리즘이 최소 O(N)이 되어버려 서로 비교하는 의미가 없어지기 때문입니다.
  2. 시간이 좋다고 공간도 좋은 건 아니다 — 완전히 독립적인 두 축이다. 응용④ merge_sorted는 시간 O(N+M)으로 훌륭하지만, 새 리스트 result를 만들기 때문에 공간도 O(N+M)입니다. 반면 응용② remove_duplicates는 시간 O(N)이면서 공간은 O(1)입니다(제자리 수정). 둘은 따로따로 분석해야 합니다.
  3. 파이썬 슬라이싱은 공짜가 아니다. 응용④에서 썼던 a[i:], b[j:] 같은 슬라이싱은 그 부분을 "가리키기만" 하는 게 아니라 새로운 리스트를 통째로 복사합니다. 즉 a[i:] 한 줄만으로도 그 자체로 O(len(a)-i)만큼의 시간과 공간을 씁니다. 겉보기에 간단해 보이는 코드도 공짜가 아니라는 걸 기억하세요.
  4. 재귀는 숨어있는 공간 비용이 있다. 함수가 스스로를 N번 호출하는 재귀라면, 가장 안쪽 호출이 끝나기 전까지 N개의 호출이 스택에 계속 쌓여 있어야 하므로 O(N)의 추가 공간이 필요합니다. 반복문으로 짠 코드와 똑같은 결과를 내더라도, 재귀는 이 숨은 비용을 항상 동반합니다.
  5. "in-place(제자리에서)"의 정확한 뜻은 "추가 공간 O(1)"이다. 응용②가 "추가 배열을 만들면 안 된다"고 했던 이유가 바로 이것입니다 — 입력 배열 자체를 답으로 재활용해서 별도의 메모리를 아끼는 것이 in-place의 핵심입니다.

실습 01 · 성취기준 직결

list 연산별 성능 벤치마크

목표: append(끝 삽입) vs insert(0, x)(앞 삽입)의 실행 시간을 직접 측정해서, 이론 곡선과 실측 곡선이 실제로 일치하는지 검증합니다.

time.perf_counter()는 코드의 실행 시간을 측정할 때 쓰는 파이썬 표준 함수입니다. 호출한 순간의 시각을 아주 정밀한 단위(초 단위, 소수점 이하 나노초 수준)로 돌려주는데, 절대적인 시각 자체는 의미가 없고 두 시점의 차이만 의미가 있습니다. 그래서 항상 아래처럼 "측정 시작 전에 한 번, 끝난 직후에 한 번" 호출해서 그 차이를 구하는 방식으로 씁니다.

start = time.perf_counter()
# ... 시간을 재고 싶은 코드 ...
elapsed = time.perf_counter() - start   # 걸린 시간(초)

비슷한 함수로 time.time()도 있지만, time.time()은 시스템 시계(사용자가 시간을 바꾸면 값이 튈 수 있음)를 기준으로 하는 반면 time.perf_counter()는 그런 영향을 받지 않는 단조 증가(monotonic) 시계라서, 짧은 코드의 실행 시간을 정밀하게 벤치마크할 때는 항상 이쪽을 씁니다.

import time

def bench_append(n):
    lst = []
    start = time.perf_counter()
    for i in range(n):
        lst.append(i)
    return time.perf_counter() - start

def bench_insert_front(n):
    lst = []
    start = time.perf_counter()
    for i in range(n):
        lst.insert(0, i)  # 항상 맨 앞에 삽입
    return time.perf_counter() - start

for n in [1000, 2000, 4000, 8000, 16000]:
    print(n, bench_append(n), bench_insert_front(n))
  1. 위 코드를 그대로 실행하고, n이 두 배가 될 때마다 각 함수의 실행 시간이 몇 배로 느는지 표로 기록하세요.
  2. bench_append의 시간은 n에 거의 비례해서 늘어나는데(선형), bench_insert_front는 훨씬 가파르게 늘어나는 이유를 "책장 비유"로 설명해 보세요.
  3. 도전: collections.deque로 같은 실험을 반복하면 appendleft의 시간이 어떻게 달라질까요? 직접 실행해서 확인하세요.

🔎 힌트
리스트를 한 번만 순회하면서 지금까지 본 값 중 최댓값과 최솟값을 각각 변수에 갱신하면 됩니다. 
def max_min_gap(nums):
    hi, lo = nums[0], nums[0]
    for x in nums[1:]:
        hi = max(hi, x)
        lo = min(lo, x)
    return hi - lo
sorted()를 쓰면 O(N log N)이지만, 이 방법은 리스트를 딱 한 번만 훑으므로 O(N)입니다. "정렬해서 양 끝을 본다"는 접근이 항상 최선은 아니라는 걸 보여주는 예시입니다.

응용 ② — 정렬된 배열에서 중복 제거 (투 포인터: 느린/빠른 포인터)

이미 정렬된 배열 nums에서 중복된 값을 제자리(in-place)에서 제거하고, 남은 고유한 원소의 개수를 반환하세요. 추가 배열을 만들면 안 됩니다.

알고리즘

  1. 배열이 비어있으면 그냥 0을 반환하고 끝낸다.
  2. "지금까지 확정된 고유값들의 마지막 위치"를 가리키는 slow를 0으로 시작한다.
  3. "새로운 값을 찾아 나서는" fast를 1번 인덱스부터 끝까지 한 칸씩 옮기며 확인한다.
  4. fast가 가리키는 값이 slow가 가리키는 값과 다르면: 새로운 고유값을 찾은 것이므로 slow를 한 칸 옮기고, 그 자리에 fast가 가리키는 값을 옮겨 적는다.
  5. fast가 가리키는 값이 slow가 가리키는 값과 같으면(중복이면): 아무것도 하지 않고 fast만 계속 전진시킨다.
  6. fast가 끝까지 다 돌면, (slow + 1)이 곧 고유한 원소의 개수다.

이 문제는 "제자리(in-place)"에서 수정하는 것이 조건이므로, 함수가 새 배열을 만들어 반환하지 않고 원본 nums를 직접 바꿔버립니다. 그래서 반환값은 "결과 배열"이 아니라 "결과가 몇 번째 인덱스까지인지"를 알려주는 개수(정수)입니다. 호출하는 쪽에서 그 개수를 이용해 실제 결과를 잘라내면 됩니다.

def remove_duplicates(nums):
    if not nums:
        return 0
    slow = 0
    for fast in range(1, len(nums)):
        if nums[fast] != nums[slow]:
            slow += 1
            nums[slow] = nums[fast]
    return slow + 1

# ── 사용 예시 ──
nums = [1, 1, 2, 3, 3, 3, 4]
k = remove_duplicates(nums)

print(k)         # 4                      ← 고유한 원소의 개수
print(nums[:k])  # [1, 2, 3, 4]           ← 실제 고유값 (이게 진짜 결과!)
print(nums)      # [1, 2, 3, 4, 3, 3, 4]  ← 원본 배열 전체 (k 이후는 의미 없는 값)

nums는 함수 안에서 직접 수정되었으므로(참조를 통한 변경 — 1주차에서 배운 내용과 연결됩니다), 함수가 끝난 뒤에도 nums 자체가 바뀌어 있습니다. nums[:k]처럼 반환된 개수만큼 슬라이싱해야 비로소 "중복이 제거된 배열"을 얻을 수 있습니다.

응용 ④ — 정렬된 두 배열 병합하기

이미 정렬된 두 리스트 a, b를 하나의 정렬된 리스트로 합치는 함수를 O(N+M)에 작성하세요 (N, M은 각 리스트의 길이). 병합 정렬(Merge Sort)의 핵심 부품이기도 합니다.

알고리즘

  1. 결과를 담을 빈 리스트를 하나 만들고, a와 b를 각각 가리킬 포인터 i, j를 0으로 시작한다.
  2. 두 포인터가 아직 각자 배열의 끝에 도달하지 않은 동안 반복한다.
  3. 두 포인터가 가리키는 값을 비교해서, 더 작은 쪽을 결과 리스트 끝에 담고 그 포인터만 한 칸 전진시킨다.
  4. 둘 중 한쪽 배열이 먼저 끝나면 반복을 멈춘다.
  5. 아직 남아있는(끝나지 않은) 배열의 나머지 부분을, 비교 없이 그대로 결과 리스트 뒤에 통째로 이어 붙인다 — 이미 정렬되어 있으므로 안전하다.
def merge_sorted(a, b):
    result = []
    i = j = 0
    while i < len(a) and j < len(b):
        if a[i] <= b[j]:
            result.append(a[i]); i += 1
        else:
            ____ # 힌트: b쪽 원소를 담고, j를 옮긴다
    result.extend(a[i:])
    result.extend(b[j:])
    return result

while 루프는 a와 b 중 어느 한쪽이 먼저 바닥나는 순간 끝납니다. 이때 아직 남아있는 배열은 이미 정렬되어 있으므로, 남은 부분을 통째로 result 뒤에 이어 붙이기만 하면 됩니다 — 이게 result.extend(a[i:])와 result.extend(b[j:])가 하는 일입니다. a[i:]는 "인덱스 i부터 끝까지"를 의미하므로, 만약 a가 이미 다 소진됐다면(i == len(a)) a[i:]는 빈 리스트가 되어 아무 일도 일어나지 않습니다. 즉 두 줄 중 실제로 무언가를 추가하는 건 항상 둘 중 하나뿐이며, 어느 쪽이 남았는지 따로 if문으로 검사할 필요 없이 슬라이싱이 자동으로 처리해 줍니다.

🔎 힌트 및 정답
빈칸은 result.append(b[j]); j += 1입니다. 두 포인터 i, j가 각자의 배열에서 한 방향으로만 전진하며 서로 비교하는 것도 투 포인터의 한 형태입니다. 각 포인터는 자기 배열을 한 번씩만 훑으므로 전체는 O(N+M)이며, 브루트포스로 합친 뒤 다시 정렬하면 O((N+M) log(N+M))이 되므로 훨씬 비효율적입니다.

def build_pairs(nums):
