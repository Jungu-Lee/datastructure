연결 리스트 버그 헌트

이번에는 새로 만드는 것이 아니라, 이미 짜여 있는 코드를 읽고 고친다. 아래 LinkedList 클래스는 겉보기엔 그럴듯하게 돌아가지만 정확히 5개의 버그가 숨어 있다. 실무에서 연결 리스트가 무너지는 방식이 바로 이런 모습이다 — 에러 없이 조용히 노드를 잃어버린다.

01 상황

AI 사용 금지

이 과제는 AI 도구(챗봇 등)의 사용을 전면 금지한다. 주어진 코드를 AI에 입력하면 버그 5개의 위치와 원인을 즉시 알려주기 때문에, 이 과제가 측정하려는 능력 — 남이 쓴 코드를 읽고 불변식과 대조해 결함을 스스로 찾아내는 능력 — 이 전혀 측정되지 않는다.

  • 주어진 코드의 전체 또는 일부를 AI에 입력하는 행위
  • 버그의 위치·원인·수정 방법을 AI에게 묻는 행위
  • 수정 코드나 회귀 테스트 코드를 AI에게 생성받는 행위
  • 서술형 답안을 AI로 작성하는 행위

위반 시 「자료구조 교수학습 및 평가운영 계획서」의 처리 방안을 따른다 — 1차 위반은 재작성 및 해당 과제 50% 감점, 2차 위반 또는 명백한 대필은 0점 처리. 다만 제출 전 스스로 신고한 경우에는 해당 부분을 본인이 다시 작성하는 조건으로 감경한다.

선배가 작성해둔 LinkedList 클래스를 인수인계 받았다. Node 클래스와 append()는 정상 동작이 확인되었고, 나머지 메서드 어딘가에 버그가 정확히 5개 있다. 각 메서드가 무엇을 해야 하는지는 docstring에 적혀 있다.

먼저 주어진 파일을 그대로 실행해보면 다음과 같은 출력이 나온다.

append 후 : None -> 10 -> 20 -> 30 -> None
get(0) : 20
insert_at(3,40): None -> 10 -> 20 -> 30 -> 40 -> None
append(50) 후 : None -> 10 -> 20 -> 30 -> 50 -> None
주의. 이 출력에 드러나는 버그는 전부가 아니다. 위 드라이버가 건드리지 않는 메서드에도 버그가 숨어 있으니, 출력만 보고 판단하지 말고 모든 메서드를 불변식과 대조하며 읽어야 한다.

02 이 클래스가 지켜야 할 불변식

버그를 "느낌"으로 찾으면 놓친다. 이 클래스는 아래 네 가지 약속을 모든 연산 전후에 항상 지켜야 한다. 각 메서드를 한 줄씩 읽으면서 "이 코드가 이 약속을 깨뜨리는가?"를 묻는 것이 이번 과제의 방법이다.

①

더미 노드는 데이터가 아니다. dummy는 값 없는 가짜 첫 칸이며, 리스트의 진짜 첫 노드는 언제나 dummy.next다. 사용자에게 dummy의 내용이 노출되어서는 안 된다.

②

tail은 항상 마지막 노드를 가리킨다. 리스트가 비어 있으면 tail은 dummy를 가리킨다. 노드를 넣거나 뺀 뒤에도 이 관계가 유지되어야 다음 append()가 O(1)로 정확히 동작한다.

③

연결은 이전 노드의 next로만 바뀐다. dummy에서 next를 따라가면 모든 노드를 정확히 한 번씩 지나 None에 도달해야 한다. 노드를 실제로 빼내거나 끼우는 일은 이전 노드의 next를 다시 연결하는 것으로만 이루어진다.

④

인덱스는 0부터 시작한다. index = 0은 dummy.next, 즉 진짜 첫 노드를 뜻한다. 빈 리스트에 대한 연산은 조용히 실패하지 않고 docstring이 약속한 예외를 발생시켜야 한다.

불변식을 모두 지킨 정상 상태 · append(10), append(20), append(30) 이후

이것이 정상 상태다. dummy는 값으로 세지 않고(①), tail은 마지막 노드 30을 가리키며(②), dummy에서 next를 따라가면 모든 노드를 한 번씩 지나 None에 닿고(③), 진짜 첫 노드가 index 0이다(④). 버그가 있는 메서드는 이 그림 중 어느 화살표를 잘못 옮기는지를 생각하며 찾아라.

03 주어진 코드

함께 배포된 3주차_과제2_buggy_linked_list.py의 내용이다. Node와 append()는 정상이다.

class LinkedList:
    """더미 노드 + tail 포인터 기반 단일 연결 리스트."""

    def __init__(self):
        self.dummy = Node(None)
        self.tail = self.dummy

    def append(self, value):
        """리스트 맨 뒤에 value를 O(1)로 추가한다."""
        new_node = Node(value)
        self.tail.next = new_node
        self.tail = new_node

    def insert_at(self, index, value):
        """index 위치 앞에 value를 삽입한다. index == 길이면 맨 뒤에 붙는다."""
        new_node = Node(value)
        prev = self.dummy
        for _ in range(index):
            prev = prev.next
        new_node.next = prev.next
        prev.next = new_node

    def delete_value(self, value):
        """value를 가진 첫 노드를 삭제한다. 삭제하면 True, 없으면 False."""
        prev, cur = self.dummy, self.dummy.next
        while cur:
            if cur.data == value:
                if cur is self.tail:
                    self.tail = prev
                cur = cur.next
                return True
            prev, cur = cur, cur.next
        return False

    def get(self, index):
        """index번째(0부터 시작) 노드의 데이터를 반환한다."""
        cur = self.dummy.next
        for _ in range(index + 1):
            cur = cur.next
        return cur.data

    def pop_front(self):
        """맨 앞 노드를 제거하고 그 데이터를 반환한다.
        리스트가 비어 있으면 IndexError를 발생시켜야 한다."""
        first = self.dummy.next
        self.dummy.next = first.next
        if first is self.tail:
            self.tail = self.dummy
        return first.data

    def __iter__(self):
        """head(진짜 첫 노드)부터 마지막 노드까지 데이터를 순서대로 내놓는다."""
        cur = self.dummy
        while cur:
            yield cur.data
            cur = cur.next

04 요구사항

① 버그 리포트 작성 (5개)

찾아낸 버그 5개를 아래 형식의 표로 정리한다. "증상"과 "원인"을 반드시 구분해서 쓸 것 — 증상은 눈에 보이는 잘못된 동작이고, 원인은 어떤 줄이 어떤 불변식을 어떻게 깨뜨렸는지다.

#메서드증상원인 (깨진 불변식)수정 내용
1예) __iter__순회하면 맨 앞에 None이 끼어든다더미를 데이터로 취급 — 불변식 ①cur = self.dummy → self.dummy.next
2~5직접 채운다
힌트. 5개 중 최소 하나는 에러를 내지 않고 조용히 데이터를 잃어버리는 종류다. 이런 버그는 "실행이 되니까 맞겠지"로 넘어가면 절대 못 잡는다. 각 메서드를 실행한 직후에 tail이 어디를 가리키고 있는지 손으로 그려보면 드러난다.

② 수정 코드 제출

  • ·버그 5개를 모두 수정한 LinkedList 전체 코드를 제출한다.
  • ·수정한 줄마다 # [버그 N 수정] ... 형식의 주석으로 왜 이렇게 고쳤는지 한 줄 설명을 남긴다.
  • ·메서드의 시간복잡도를 원래보다 나쁘게 만들지 말 것 — 예를 들어 append()는 수정 후에도 반드시 O(1)이어야 한다. (tail을 버리고 매번 순회하는 식의 "고침"은 인정하지 않는다.)

③ 회귀 테스트 작성 (5개 이상)

버그마다 그 버그를 정확히 잡아내는 테스트를 하나씩 작성한다. 좋은 회귀 테스트의 조건은 다음과 같다.

  • ·수정 전 코드에서는 반드시 실패하고, 수정 후에는 통과해야 한다. (둘 다 확인해서 제출할 것)
  • ·assert로 기대값을 명시한다. 화면에 출력만 하고 눈으로 확인하는 것은 테스트가 아니다.
  • ·함수 이름만 읽어도 무엇을 검증하는지 알 수 있게 짓는다. (예: test_insert_at_end_keeps_tail_valid)
가장 중요한 채점 포인트. "수정 전 코드에서 실패한다"를 확인하지 않은 테스트는 점수를 받지 못한다. 버그를 못 잡는 테스트는 통과해도 아무것도 보장하지 않기 때문이다.

05 서술형 질문

아래 질문에 각 3~5문장으로 답하시오.

  1. 이번에 찾은 버그 중 가장 발견하기 어려웠던 것을 하나 고르고, 왜 어려웠는지 설명하시오. (에러가 나지 않아서? 특정 순서로 호출할 때만 드러나서?)
  2. 버그 중에는 tail 포인터와 관련된 것이 있다. tail을 아예 두지 않고 append()마다 head부터 끝까지 순회하도록 만들면 이 부류의 버그는 원천적으로 사라진다. 그럼에도 tail을 유지하는 이유는 무엇인가? 얻는 것과 잃는 것을 복잡도 관점에서 설명하시오.
  3. 더미 노드는 "빈 리스트 예외를 없애준다"고 배웠다. 그런데 이번 코드에는 더미 노드가 있음에도 빈 리스트에서 터지는 버그가 존재했다. 더미 노드가 없애주는 예외와 없애주지 못하는 예외는 각각 어떤 것인지 구분해서 설명하시오.

07 제출 전 자가 점검

제출하기 전에 아래 항목을 스스로 점검해보자.

  • 버그 5개를 모두 찾았고, 각각 어떤 불변식을 깨뜨렸는지 지목했다.
  • 증상(눈에 보이는 잘못된 동작)과 원인(잘못된 코드 줄)을 구분해서 적었다.
  • 수정한 줄마다 왜 그렇게 고쳤는지 주석을 남겼다.
  • 수정 후에도 append()가 O(1)인지 확인했다 (tail을 버리지 않았다).
  • 회귀 테스트를 수정 전 코드에 돌려서 실제로 실패하는 것을 확인했다.
  • 회귀 테스트를 수정 후 코드에 돌려서 전부 통과하는 것을 확인했다.

  • 버그 탐색·수정·테스트 작성 전 과정에서 AI 도구를 사용하지 않았다.
