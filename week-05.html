4주차와의 연결

스택과 큐는 사실 연결 리스트(혹은 배열)에 "이 끝에서만 넣고 뺀다"는 규칙을 하나 얹은 것이다. 4주차의 head 삽입이 바로 스택의 push 연산과 같은 O(1) 연산이다.

02 이론

LIFO: 접시 더미

싱크대에 쌓인 접시는 맨 위에 놓은 것을 맨 먼저 꺼내 쓴다(Last In, First Out). 함수 호출 스택, 되돌리기(Undo), 괄호 짝 맞추기가 전형적인 스택 문제다. 파이썬에서는 list의 append/pop을 그대로 스택으로 쓸 수 있다 — 둘 다 O(1)이기 때문이다.

FIFO: 매표소 대기열

줄을 선 순서대로 표를 받는다(First In, First Out). 그런데 list.pop(0)은 앞의 모든 요소를 당겨야 해서 O(N)이다 — 리스트를 큐로 쓰면 앞에서 뺄 때마다 성능이 저하된다. 이 문제를 해결하는 것이 collections.deque다. 양쪽 끝 모두 O(1)로 삽입/삭제가 가능한 이중 연결 리스트 기반 구조다.

03 연결 리스트로 구현하기

지금까지는 파이썬이 이미 완성해 둔 list와 deque로 스택·큐를 썼다. 이번에는 3·4주차에서 만든 Node를 직접 이어 붙여, 그 도구들이 내부에서 어떤 원리로 O(1)을 만들어내는지 밑바닥부터 확인해본다. 1절에서 언급했듯 "4주차의 head 삽입이 곧 스택의 push"라는 말을 코드로 직접 증명하는 셈이다.

스택 — 단일 연결 리스트 + head 포인터 하나

스택은 항상 한쪽 끝에서만 넣고 뺀다. 그 끝을 연결 리스트의 head로 삼으면 push와 pop 모두 head 딱 하나만 조작하면 끝난다 — 중간 노드를 순회할 일이 전혀 없다.

알고리즘 — push(data)
  • 1새 Node를 만들어 data를 담는다.
  • 2새 Node의 next가 현재 head를 가리키게 연결한다.
  • 3head를 새 Node로 교체한다.
알고리즘 — pop()
  • 1head가 None이면 스택이 비었다는 뜻이므로 예외를 발생시킨다.
  • 2head가 가리키는 Node의 data를 꺼내 임시로 저장한다.
  • 3head를 head.next로 옮겨 기존 head를 리스트에서 분리한다.
  • 4저장해둔 data를 반환한다.
class Node:
    __slots__ = ('data', 'next')  # 3주차에서 배운 메모리 최적화 기법을 그대로 사용
    def __init__(self, data):
        self.data = data
        self.next = None


class LinkedStack:
    """단일 연결 리스트로 구현한 스택(LIFO). head 포인터 하나만 쓴다."""
    __slots__ = ('head', '_size')

    def __init__(self):
        self.head = None        # 스택의 top을 가리키는 포인터
        self._size = 0

    def push(self, data):
        # 알고리즘: 새 노드를 만들고 head 앞에 끼워 넣는다 — O(1)
        new_node = Node(data)
        new_node.next = self.head      # 새 노드가 기존 head를 가리키게 연결
        self.head = new_node           # head를 새 노드로 교체
        self._size += 1

    def pop(self):
        # 알고리즘: head가 가리키는 노드를 떼어내고 반환한다 — O(1)
        if self.head is None:
            raise IndexError('pop from empty stack')
        popped = self.head
        self.head = self.head.next     # head를 한 칸 옮겨 기존 head를 분리
        popped.next = None         # 끊어낸 노드가 리스트를 계속 참조하지 않도록 정리
        self._size -= 1
        return popped.data

    def peek(self):
        if self.head is None:
            raise IndexError('peek from empty stack')
        return self.head.data        # 꺼내지 않고 top 값만 확인 — O(1)

    def is_empty(self):
        return self.head is None

    def __len__(self):
        return self._size

list 기반 스택도 append/pop이 O(1)인데 왜 굳이 연결 리스트로 다시 만들까? 사실 list의 O(1)은 상각(amortized) O(1)이다 — 내부 배열이 꽉 차면 가끔 한 번씩 더 큰 배열로 재할당하는 비용이 숨어 있다(이 '상각'이 무엇인지는 05절 심화의 읽기 자료에서 자세히 다룬다). LinkedStack은 매번 새 Node 하나만 만들므로 최악의 경우에도 진짜 O(1)을 보장한다.

큐 — 단일 연결 리스트 + head·tail 포인터 두 개

큐는 넣는 곳(rear)과 빼는 곳(front)이 다르다. head 하나만 쓰면 rear 쪽 삽입마다 리스트 끝까지 순회해야 해서 O(N)이 되어버린다 — 이론에서 본 list.pop(0)의 함정과 정확히 같다. tail 포인터를 하나 더 유지해야 양쪽 모두 O(1)을 보장할 수 있다.

알고리즘 — enqueue(data)
  • 1새 Node를 만들어 data를 담는다.
  • 2큐가 비어 있다면(tail이 None) head와 tail을 모두 새 Node로 설정한다.
  • 3비어 있지 않다면 기존 tail의 next를 새 Node로 연결하고, tail을 새 Node로 옮긴다.
알고리즘 — dequeue()
  • 1head가 None이면 큐가 비었다는 뜻이므로 예외를 발생시킨다.
  • 2head가 가리키는 Node의 data를 꺼내 임시로 저장한다.
  • 3head를 head.next로 옮긴다.
  • 4그 결과 head가 None이 되었다면(마지막 노드를 꺼낸 경우) tail도 함께 None으로 비운다.
  • 5저장해둔 data를 반환한다.
class LinkedQueue:
    """단일 연결 리스트 + head·tail 포인터로 구현한 큐(FIFO)."""
    __slots__ = ('head', 'tail', '_size')

    def __init__(self):
        self.head = None    # front: dequeue가 일어나는 쪽
        self.tail = None    # rear : enqueue가 일어나는 쪽
        self._size = 0

    def enqueue(self, data):
        # 알고리즘: tail 뒤에 새 노드를 붙이고 tail을 갱신한다 — O(1)
        new_node = Node(data)
        if self.tail is None:            # 빈 큐였다면 head·tail이 같은 노드를 가리켜야 함
            self.head = self.tail = new_node
        else:
            self.tail.next = new_node    # 기존 tail의 next를 새 노드로 연결
            self.tail = new_node         # tail을 새 노드로 이동
        self._size += 1

    def dequeue(self):
        # 알고리즘: head를 떼어내고 head를 한 칸 전진시킨다 — O(1)
        if self.head is None:
            raise IndexError('dequeue from empty queue')
        removed = self.head
        self.head = self.head.next
        if self.head is None:             # 마지막 노드를 꺼낸 경우 — tail도 함께 비워야 한다!
            self.tail = None             # (빠뜨리면 tail이 유령 노드를 계속 가리키는 버그가 생긴다)
        removed.next = None
        self._size -= 1
        return removed.data

    def is_empty(self):
        return self.head is None

    def __len__(self):
        return self._size

04 대표 알고리즘 예제

스택과 큐가 실제로 어떤 문제를 "우아하게" 푸는지 세 가지 예제로 확인한다. 모두 먼저 알고리즘을 말로 정리한 뒤, 그 순서를 그대로 코드로 옮긴다 — 이때 list나 deque가 아니라 03절에서 직접 만든 LinkedStack·LinkedQueue를 사용해, "우리가 만든 자료구조"가 실전 문제를 그대로 풀어낸다는 것을 확인한다.

스택 예제 ① — 후위 표기법(Postfix) 계산기

"(3 + 4) * 2" 같은 일반적인 수식(중위 표기법)은 괄호와 연산자 우선순위를 따져야 계산 순서를 알 수 있다. 반면 후위 표기법 "3 4 + 2 *"는 토큰을 왼쪽부터 딱 한 번씩만 읽으면서 계산할 수 있다 — 연산자를 만나면 "가장 최근에 나온 두 값"을 꺼내 계산하면 되기 때문이다. "가장 최근 것부터" 처리한다는 점에서 스택이 정확히 들어맞는다.

알고리즘 — 후위 표기법 계산
  • 1수식을 공백 기준으로 토큰(숫자/연산자)으로 나눈다.
  • 2토큰을 순서대로 하나씩 확인한다.
  • 3숫자면 스택에 push한다.
  • 4연산자면 스택에서 두 번 pop한다 — 나중에 나온 값이 오른쪽 피연산자다.
  • 5두 값으로 연산을 수행하고, 결과를 다시 스택에 push한다.
  • 6모든 토큰을 처리하고 나면 스택에 남은 값 하나가 최종 결과다.
# 03절에서 만든 LinkedStack을 그대로 사용한다
def eval_postfix(expression):
    stack = LinkedStack()
    ops = {
        '+': lambda a, b: a + b,
        '-': lambda a, b: a - b,
        '*': lambda a, b: a * b,
        '/': lambda a, b: a / b,
    }
    for token in expression.split():         # 공백으로 토큰 분리
        if token in ops:
            b = stack.pop()                     # 나중에 push된 피연산자 (오른쪽 항)
            a = stack.pop()                     # 먼저 push된 피연산자 (왼쪽 항)
            stack.push(ops[token](a, b))        # 연산 결과를 다시 push
        else:
            stack.push(float(token))            # 숫자 토큰은 그대로 push
    return stack.pop()                           # 마지막 남은 값이 최종 결과


# "3 4 + 2 *" -> (3 + 4) * 2 = 14.0
print(eval_postfix("3 4 + 2 *"))

스택 예제 ② — 일일 온도 (모노토닉 스택)

새 용어 · 모노토닉 스택 (Monotonic Stack)

모노토닉(monotonic)은 수학에서 "단조로운", 즉 한 방향으로만 증가하거나 한 방향으로만 감소하는 성질을 뜻한다. 모노토닉 스택은 이 성질을 항상 지키도록 관리하는 스택이다 — 즉 스택 안의 값이 바닥에서 top까지 항상 정렬된 상태(계속 증가 또는 계속 감소)를 유지한다.

비결은 push하기 전에 정렬을 깨뜨리는 기존 값들을 먼저 pop해서 걷어내는 것이다. 예를 들어 "감소하는 모노토닉 스택"이라면, 새로 들어올 값보다 작은 top들을 전부 꺼낸 뒤에 push한다. 그러면 스택은 언제나 위로 갈수록 작아지는 상태를 유지한다.

왜 유용할까? "각 원소의 오른쪽(또는 왼쪽)에서 자기보다 크거나 작은 첫 번째 원소를 찾아라" 같은 문제에서, 이 정렬 상태 덕분에 모든 원소를 다시 비교하지 않아도 답을 찾을 수 있다. 겉보기엔 이중 반복문(O(N²))이 필요해 보여도, 각 원소가 스택에 딱 한 번 들어가고 한 번 나오므로 전체가 O(N)으로 끝난다. 아래 일일 온도 문제가 바로 그 대표 예다.

매일의 기온이 담긴 리스트에서 "각 날짜마다 더 따뜻한 날이 오기까지 며칠을 기다려야 하는가"를 구하는 문제다(더 따뜻한 날이 없으면 0). 각 날짜마다 이후 날짜를 전부 훑으면 O(N²)이 걸린다. 여기서는 온도가 감소하는 모노토닉 스택에 "아직 더 따뜻한 날을 못 만난 날짜"의 인덱스만 쌓아둔다. 오늘이 스택 top보다 따뜻하면, 그 top 날짜는 기다림이 끝난 것이므로 pop하며 답을 기록한다. 각 날짜는 스택에 딱 한 번 들어가고 한 번만 나오므로, while문이 반복되더라도 전체는 O(N)으로 끝난다.

알고리즘 — 일일 온도
  • 1정답을 담을 배열을 0으로 채워 준비한다.
  • 2"답을 못 찾은 날짜의 인덱스"를 담을 빈 스택을 준비한다.
  • 3날짜를 순서대로 확인한다.
  • 4스택이 비어있지 않고 스택 top 날짜의 온도가 오늘 온도보다 낮은 동안, top을 pop하며 (오늘 인덱스 − pop한 인덱스)를 그 날짜의 정답으로 기록한다.
  • 5오늘 날짜의 인덱스를 스택에 push한다.
  • 6모든 날짜 처리 후 스택에 남은 인덱스는 더 따뜻한 날이 없었던 것이므로 0으로 둔다.
# 03절에서 만든 LinkedStack을 그대로 사용한다
def daily_temperatures(temps):
    n = len(temps)
    answer = [0] * n            # 기본값 0: "더 따뜻한 날이 오지 않음"
    stack = LinkedStack()       # 아직 답을 못 찾은 날짜의 인덱스 (아래→위로 온도가 감소하는 모노토닉 스택)

    for today, temp in enumerate(temps):
        # 오늘 온도가 스택 top 날짜의 온도보다 높다면, top 날짜의 '기다림'이 끝난 것
        while not stack.is_empty() and temps[stack.peek()] < temp:
            waiting_day = stack.pop()                  # 정답을 찾은 날짜를 꺼낸다
            answer[waiting_day] = today - waiting_day  # 며칠을 기다렸는지 기록
        stack.push(today)                              # 오늘은 아직 정답을 모르므로 push

    return answer


# [22,23,24,20,18,21,25,22] -> [1,1,4,2,1,1,0,0]
print(daily_temperatures([22, 23, 24, 20, 18, 21, 25, 22]))

큐 예제 — 라운드 로빈(Round-Robin) CPU 스케줄링 시뮬레이션

여러 프로세스가 CPU 하나를 나눠 써야 할 때, 각 프로세스에 정해진 시간(quantum)만 주고 끝나지 않으면 줄 맨 뒤로 보내는 방식이다. "먼저 온 순서대로 실행하고, 끝나지 않으면 다시 줄을 선다"는 규칙 자체가 FIFO 큐 그대로다 — 03절에서 만든 LinkedQueue가 정확히 이 역할을 한다.

알고리즘 — 라운드 로빈
  • 1모든 프로세스를 (이름, 남은 실행시간)으로 큐에 넣는다.
  • 2큐가 빌 때까지 반복한다.
  • 3큐 맨 앞 프로세스를 꺼낸다.
  • 4quantum과 남은 실행시간 중 작은 값만큼만 실행하고, 남은 실행시간에서 뺀다.
  • 5남은 실행시간이 0보다 크면 큐 맨 뒤에 다시 넣는다.
  • 60이 되면 큐에 다시 넣지 않고 종료 처리한다.
# 03절에서 만든 LinkedQueue를 그대로 사용한다
def round_robin(processes, quantum):
    """processes: [(이름, 필요시간), ...]  quantum: 한 번에 줄 수 있는 최대 실행시간"""
    queue = LinkedQueue()
    for p in processes:
        queue.enqueue(p)                     # 도착한 순서대로 큐에 적재 (FIFO)
    timeline = []                            # (완료 시각, 이름, 이번에 실행한 시간) 로그
    now = 0

    while not queue.is_empty():              # 큐가 빌 때까지 = 모든 프로세스 종료까지
        name, remaining = queue.dequeue()    # 맨 앞 프로세스를 O(1)로 꺼낸다
        run_time = min(quantum, remaining)   # 할당량과 남은 시간 중 작은 값만큼만 실행
        now += run_time
        timeline.append((now, name, run_time))
        remaining -= run_time

        if remaining > 0:
            queue.enqueue((name, remaining))  # 아직 안 끝났으면 줄 맨 뒤로 다시 O(1)

    return timeline


# A, B, C가 각각 5, 3, 7의 실행시간 필요, quantum=2
for record in round_robin([('A', 5), ('B', 3), ('C', 7)], quantum=2):
    print(record)

여기서는 지금까지 배운 스택·큐를 한 단계 더 밀어붙인다. 두 주제 모두 "겉으로 보이는 한계를, 관점을 바꿔 뛰어넘는다"는 공통점이 있다.

심화 ① 환형 큐 — 배열로도 O(1) 큐를 만든다

02절에서 "배열로 큐를 만들면 pop(0) 때문에 O(N)"이라고 했다. 그래서 연결 리스트나 deque를 썼다. 그런데 배열을 포기하지 않고도 이 문제를 푸는 방법이 있다. 비밀은 발상의 전환이다 — 앞에서 요소가 빠져 생긴 빈 칸을, 뒤에서 넘어온 새 요소가 재사용하게 하는 것이다. 배열의 끝과 처음을 이어 붙여 원(ring)처럼 빙 돌려 쓴다고 해서 환형 큐라 부른다.

핵심 도구는 두 개의 인덱스와 나머지 연산(%)이다. front는 꺼낼 위치, rear는 넣을 위치를 가리키고, 끝에 도달하면 (위치 + 1) % 용량으로 다시 0번 칸으로 돌아온다.

채워진 칸 front (꺼낼 자리) rear (넣을 자리)

A, B, C, D를 차례로 enqueue

[0]A
[1]B
[2]C
[3]D
[4]
[5]

front는 0번 칸, 다음에 넣을 rear 위치는 4번 칸. 아직 배열 순서대로 채워진다.

dequeue를 두 번 → A, B 제거

[0]
[1]
[2]C
[3]D
[4]
[5]

front가 0→2로 이동. 앞의 0·1번 칸이 비었지만 요소를 당기지 않는다. front만 움직일 뿐이라 O(1).

E, F, G를 enqueue → rear가 끝을 넘어 앞으로!

[0]G
[1]
[2]C
[3]D
[4]E
[5]F

rear가 4→5까지 간 뒤, 5의 다음은 (5+1) % 6 = 0. 비어 있던 0번 칸을 재사용한다. 이것이 환형 큐의 핵심 — 배열을 원처럼 빙 돌려 쓴다.

알고리즘 — enqueue(value)
  • 1큐가 가득 찼으면(size == 용량) 더 넣을 수 없으므로 예외를 발생시킨다.
  • 2넣을 위치를 계산한다: rear = (front + size) % 용량.
  • 3그 자리에 값을 저장하고 size를 1 늘린다.
알고리즘 — dequeue()
  • 1큐가 비었으면(size == 0) 예외를 발생시킨다.
  • 2front 위치의 값을 꺼내 임시로 저장한다.
  • 3front를 한 칸 전진시킨다: front = (front + 1) % 용량. 끝에서 자동으로 0번으로 돌아온다.
  • 4size를 1 줄이고 저장한 값을 반환한다.
class CircularQueue:
    """고정 크기 배열을 원처럼 돌려 쓰는 큐. 양쪽 끝 모두 O(1)."""
    def __init__(self, capacity):
        self.capacity = capacity
        self.data = [None] * capacity  # 크기가 고정된 배열
        self.front = 0                  # 다음에 꺼낼 위치
        self.size = 0                   # 현재 들어있는 개수 (front+size로 rear를 계산)

    def is_empty(self):
        return self.size == 0

    def is_full(self):
        return self.size == self.capacity

    def enqueue(self, value):
        if self.is_full():
            raise OverflowError('queue is full')
        rear = (self.front + self.size) % self.capacity  # 넣을 자리 = front에서 size칸 뒤 (원을 넘으면 앞으로)
        self.data[rear] = value
        self.size += 1

    def dequeue(self):
        if self.is_empty():
            raise IndexError('dequeue from empty queue')
        value = self.data[self.front]
        self.data[self.front] = None              # 꺼낸 칸을 비워둔다 (참조 정리)
        self.front = (self.front + 1) % self.capacity  # front를 한 칸 전진 — 끝이면 0으로 wrap
        self.size -= 1
        return value


# 용량 3짜리 큐를 돌려 쓰기
cq = CircularQueue(3)
cq.enqueue('A'); cq.enqueue('B'); cq.enqueue('C')  # 가득 참
print(cq.dequeue())     # A (front 이동)
cq.enqueue('D')         # 비워진 앞 칸을 재사용
print(cq.dequeue())     # B
왜 size를 따로 셀까?

front와 rear 인덱스만으로 상태를 관리하면, "큐가 가득 참"과 "큐가 비어 있음"이 똑같이 front == rear로 나타나는 유명한 문제가 생긴다. 이를 피하려고 흔히 "한 칸을 비워두거나" size 변수를 따로 둔다. 여기서는 이해하기 쉽도록 size를 세는 방식을 택했다.

실무에서 환형 큐는 어디에 쓰일까 — 생산자·소비자 버퍼

환형 큐의 대표 무대는 데이터를 만드는 쪽(생산자)과 쓰는 쪽(소비자)의 속도가 다를 때다. 이때 둘 사이에 고정 크기 환형 큐를 두면, 속도 차이를 버퍼가 흡수해준다. 이 버퍼를 특히 링 버퍼(ring buffer)라 부른다. 두 장면으로 보자.

심화 ② 스택 두 개로 큐 만들기

이번엔 반대로 뒤집어 보자. LIFO인 스택만 가지고 FIFO인 큐를 만들 수 있을까? 놀랍게도 스택 두 개면 된다. 직관을 깨는 결과라 면접 단골 문제이기도 하다.

아이디어는 이렇다. 스택에 한 번 뒤집힌 것을 한 번 더 뒤집으면 원래 순서로 돌아온다. 넣을 때 쌓는 스택(in)과 뺄 때 쓰는 스택(out)을 나눈다. 꺼내야 하는데 out이 비어 있으면, 그때 in을 통째로 쏟아 out으로 옮긴다 — 이 과정에서 순서가 한 번 더 뒤집혀 가장 먼저 넣은 것이 out의 맨 위로 올라온다.

알고리즘 — enqueue(value)
  • 1무조건 in 스택에 push한다. (항상 O(1))
알고리즘 — dequeue()
  • 1out 스택이 비어 있다면, in 스택이 빌 때까지 pop해서 그 값을 out에 push한다(통째로 옮기며 순서가 뒤집힘).
  • 2그래도 out이 비어 있으면 큐 전체가 빈 것이므로 예외를 발생시킨다.
  • 3out 스택에서 pop한 값을 반환한다 — 이것이 가장 먼저 들어온 값이다.
# 스택은 파이썬 list의 append/pop으로 충분하다 (둘 다 O(1))
class TwoStackQueue:
    """LIFO 스택 두 개로 FIFO 큐를 구현한다."""
    def __init__(self):
        self.in_stack = []    # enqueue가 쌓이는 곳
        self.out_stack = []   # dequeue가 꺼내 가는 곳

    def enqueue(self, value):
        self.in_stack.append(value)       # 그냥 쌓기만 하면 끝 — 항상 O(1)

    def dequeue(self):
        if not self.out_stack:            # out이 비었을 때만 옮긴다 (핵심!)
            while self.in_stack:
                # in에서 하나씩 꺼내 out에 쌓으면 순서가 뒤집힌다
                self.out_stack.append(self.in_stack.pop())
        if not self.out_stack:            # 옮겼는데도 비었으면 큐가 완전히 빈 것
            raise IndexError('dequeue from empty queue')
        return self.out_stack.pop()        # out의 top = 가장 먼저 넣은 값


q = TwoStackQueue()
q.enqueue(1); q.enqueue(2); q.enqueue(3)
print(q.dequeue())   # 1  (여기서 in[1,2,3] → out[3,2,1]로 옮겨짐)
q.enqueue(4)         # in[4]에 쌓임, out[3,2]는 그대로
print(q.dequeue())   # 2  (out에서 바로 꺼냄, 옮기지 않음)
print(q.dequeue())   # 3
print(q.dequeue())   # 4  (out이 비어서 다시 옮김)
핵심 개념 — 상각 분석

dequeue 한 번이 최악의 경우 in 전체를 옮기므로 O(N)처럼 보인다. 하지만 각 원소는 평생 딱 네 번만 만져진다: in에 push, in에서 pop, out에 push, out에서 pop. 그래서 N번 enqueue + N번 dequeue의 총 연산량은 4N에 비례 — 연산 하나당 평균으로 나누면 상각(amortized) O(1)이다. "한 번의 비싼 연산에 속지 말고 여러 번의 흐름 전체를 보라"는 것이 상각 분석의 핵심이다. 이 중요한 개념을 아래 읽기 자료에서 개념부터 차근차근 정리했다.

읽기 자료상각 분석(amortized analysis)이란?▸

이번 심화 ②와 03절에서 "상각 O(1)"이라는 말이 나왔다. 프로그래밍에서 아주 자주 등장하는 중요한 개념이니, 개념부터 차근차근 정리하자.

상각 분석은 "가끔 비싼 연산이 섞여 있어도, 여러 번의 연산을 전체로 묶어 평균 내면 한 번당 비용이 싸다"는 것을 보이는 분석법이다. 여기서 상각(償却)은 원래 회계 용어로, 큰 비용을 여러 기간에 나눠 부담한다는 뜻이다.

비유 · 연간 구독료
영상 서비스 연간 이용권을 1월 1일에 12만 원 한 번에 결제한다고 하자. 그날 하루만 보면 "이게 얼마야?" 싶지만, 1년 동안 100편을 본다면 한 편당 1,200원이다. 결제일 하루의 큰 비용에 놀라지 말고 1년 전체로 나눠 보라는 것 — 이것이 상각의 발상이다. 가끔 목돈이 나가도, 그 목돈이 이후 수많은 값싼 사건을 가능케 한다면 평균 비용은 낮다.
왜 '최악의 경우'와 다를까

보통 알고리즘은 한 번의 연산이 최악일 때 얼마나 걸리나로 평가한다(worst-case). 그런데 어떤 연산은 최악이 아주 가끔만 일어나고 대부분은 값싸다. 이럴 때 "최악 = O(N)"이라고만 하면 실제 성능을 과장하게 된다. 상각 분석은 그 비싼 경우가 얼마나 드물게 일어나는지까지 계산에 넣어 더 정직한 평균을 낸다.

중요한 구분: 상각 분석은 운 좋은 평균적 입력을 가정하는 게 아니다. 어떤 입력이 오든 연속된 N번의 총비용이 O(N)임을 보장한다. 그래서 "평균 시간 복잡도(average-case)"와는 다르다 — 이쪽은 확률에 기대지 않는다.

대표 예제 ① — 동적 배열의 append는 왜 상각 O(1)인가

파이썬의 list는 속을 들여다보면 고정 크기 배열이다. 배열은 크기가 정해져 있으므로, 정해진 칸이 꽉 찬 상태에서 또 append하려면 더 큰 배열을 새로 만들어 기존 원소를 전부 옮겨 담아야 한다. 이 "옮겨 담기"가 O(N)짜리 비싼 작업이고, 이를 재할당(reallocation)이라 부른다. 그렇다면 append는 O(N)일까? 대부분의 append는 빈 칸에 그냥 값을 넣으므로 O(1)이고, 재할당은 가끔만 일어난다. 이 "가끔"이 얼마나 드문지가 관건이다.

핵심은 배열을 얼마나 키우느냐다. 만약 꽉 찰 때마다 한 칸씩만 늘린다면 매번 재할당이 일어나 append마다 O(N) — 최악이다. 하지만 꽉 찰 때마다 용량을 두 배로 키우면 이야기가 완전히 달라진다. 용량이 1 → 2 → 4 → 8 → … 로 커지므로, N개를 담는 동안 재할당은 약 log₂N번밖에 일어나지 않는다(100만 개를 담아도 약 20번뿐이다).

총 복사량을 더해보면 (등비수열)
재할당 때마다 옮겨 담는 원소 수는 1, 2, 4, 8, …, N개다. 이걸 전부 더하면
1 + 2 + 4 + 8 + ⋯ + N = 2N − 1 ≈ 2N
즉 N개를 append하는 전 과정에서 옮겨 담은 원소는 다 합쳐도 약 2N개뿐이다. 등비수열의 합은 마지막 항의 약 2배라는 성질 덕분이다. 따라서 N번 append의 총비용은 값 넣기 N번 + 복사 약 2N번 = 약 3N에 비례하고, 이를 N으로 나누면 append 한 번당 평균 상각 O(1)이 된다.

한 칸씩 늘릴 때(총 복사 ≈ N²/2)와 두 배로 늘릴 때(총 복사 ≈ 2N)의 차이가 바로 상각의 힘이다. "가끔 터지는 O(N) 재할당"이 그 뒤로 두 배만큼 많은 값싼 append를 보장하기 때문에, 비싼 비용이 넓게 분산되어 평균이 O(1)로 내려앉는다. (참고: 실제 CPython은 정확히 2배가 아니라 약 1.125배씩 조금씩 키우지만, "일정 비율로 키운다"는 원리가 같으므로 결론도 상각 O(1)로 같다.)

대표 예제 ② — 두 스택 큐

심화 ②의 두 스택 큐도 정확히 같은 원리다. dequeue 한 번은 최악의 경우 in 전체를 옮겨 O(N)처럼 보인다. 하지만 각 원소는 평생 딱 네 번만 만져지므로(in push → in pop → out push → out pop), 원소 N개를 넣고 빼는 전체 연산량은 4N에 비례. 연산 하나당 평균으로 나누면 상각 O(1)이다. 여기서도 "한 번의 비싼 옮기기"가 그 뒤 여러 번의 값싼 dequeue를 보장한다.

두 예의 논리는 완전히 같다 — "가끔 O(N)이 터지지만, 그 비싼 연산이 그 뒤 많은 값싼 연산을 보장하므로, 전체를 나누면 O(1)". 개별 연산의 최악값에 겁먹지 말고 연산들의 흐름 전체를 보라는 것이 상각 분석의 교훈이다.
