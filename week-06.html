01 핵심 아이디어 & 핵심 질문

핵심 아이디어

수학적 해시 함수를 통해 데이터의 논리적 키를 물리적 메모리 주소로 직접 매핑하여 탐색 시간을 없앤다.

핵심 질문

수백만 개의 데이터 중 원하는 값을 어떻게 단 한 번의 탐색(O(1))으로 찾아낼 수 있을까?

5주차까지의 흐름

배열은 인덱스를 알면 O(1), 값을 몰라 처음부터 훑어야 하면 O(N)이었다. 연결 리스트도 마찬가지로 값을 찾으려면 머리부터 하나씩 따라가야 해서 O(N)이었다. 두 구조 모두 "값(키)을 아는 것"과 "그 값이 어디 있는지 아는 것" 사이에 검색이라는 간극이 있었다. 해시 테이블은 이 간극 자체를 없앤다 — 값(키)을 넣는 즉시 그 값이 있어야 할 인덱스를 함수로 계산해버리므로, 배열을 훑을 필요 없이 바로 그 칸을 확인하면 된다.

본격적으로 들어가기 전에 — 이미 쓰고 있던 dict, 몰래 들여다보기

사실 여러분은 이미 해시를 매일 쓰고 있다. 파이썬에서 d = {}라고 쓰는 순간부터다. 아래 코드를 먼저 눈으로 따라가 보자.

d = {}
d["사과"] = 1000
d["바나나"] = 2000

print(hash("사과"))    # 뭔가 아주 크고 낯선 정수 하나가 나온다
print(d["사과"])       # 1000 — 이게 순식간에 나온 이유가 바로 위 hash() 값이다

d["사과"] = 1000이라고 쓰는 순간, 파이썬은 겉으로 드러내지 않을 뿐 속으로 hash("사과")를 계산해서 그 숫자를 가지고 메모리의 정확한 칸을 찾아간다. 그래서 딕셔너리에 백만 개를 넣어놓아도, 원하는 값 하나를 찾는 데는 거의 시간이 걸리지 않는다 — 배열처럼 앞에서부터 하나하나 확인할 필요가 없다.

이 dict라는 "상자"의 크기가 어떻게 변하는지도 궁금하지 않은가? CPython(파이썬의 기본 구현체) 내부를 슬쩍 들여다보면 이렇다.

  • 초기 크기새 딕셔너리를 만들면 처음에는 딱 8칸만 할당된다. 함수에 키워드 인자를 넘길 때처럼 작은 딕셔너리가 파이썬 안에서 매우 자주 만들어지기 때문에, 처음부터 크게 잡아 메모리를 낭비하기보다 작게 시작하는 쪽을 택한 것이다.
  • 확장 시점계속 채워 넣다가 전체 칸의 2/3(약 66%)가 차는 순간, 파이썬은 자동으로 더 큰 테이블을 만들고 기존 항목을 전부 다시 해시해 옮긴다(Rehashing) — 바로 뒤에서 배울 "적재율" 개념이 실제로 작동하는 순간이다.
  • 확장 배율보통은 기존의 4배로 커지지만, 원소가 5만 개를 넘어서면 그때부터는 2배씩만 커진다 — 딕셔너리가 이미 커진 상태에서 계속 4배씩 불리면 메모리가 너무 급격히 늘어나기 때문이다.

hash()가 왜 매번 저렇게 낯선 값을 내놓는지, 그 값으로 어떻게 정확한 칸을 찾아가는지, 그리고 서로 다른 두 키가 같은 칸을 놓고 부딪히면 무슨 일이 벌어지는지 — 이 세 가지가 이번 시간의 전부다. 이제 하나씩 뜯어보자.

02 이론

마법의 우편 분류기

우편물의 우편번호를 보고 즉시 어느 칸에 넣을지 정하는 자동 분류기처럼, 해시 함수는 키(key)를 입력받아 저장할 배열의 인덱스를 즉시 계산한다. 탐색할 때도 같은 함수로 인덱스를 다시 계산하면 바로 그 칸을 확인하면 되므로 평균 O(1)이다. 이 아이디어를 수식으로 쓰면 index = h(key)다. 가장 단순한 형태는 나눗셈법(Division Method)으로, 키를 정수로 바꾼 뒤 테이블 크기 m으로 나눈 나머지를 인덱스로 쓴다 — h(k) = k mod m. 문자열 키는 문자 코드를 합산하거나 다항식으로 조합해 먼저 정수로 바꾼 뒤 같은 방식을 적용한다.

좋은 해시 함수의 조건

  • 1결정성(Deterministic) — 같은 키를 넣으면 언제나 같은 인덱스가 나와야 한다. 그래야 저장할 때 쓴 함수로 나중에 탐색도 할 수 있다.
  • 2균등 분포(Uniform Distribution) — 키들이 특정 칸에 몰리지 않고 테이블 전체에 고르게 퍼져야 한다. 한쪽에 쏠리면 그 칸만 리스트가 길어져 사실상 O(N)에 가까워진다.
  • 3빠른 계산 — 해시 함수 자체가 느리면 O(1)이라는 말이 무의미해진다. 상수 시간에 계산되어야 한다.

테이블 크기 m은 보통 소수(prime number)로 고른다. 키 값들이 특정 배수(짝수, 10의 배수 등)로 몰려 있어도, 소수로 나누면 나머지가 훨씬 고르게 흩어지기 때문이다.

충돌은 수학적으로 피할 수 없다

비둘기집 원리(Pigeonhole Principle) — 키가 될 수 있는 값의 가짓수는 사실상 무한(모든 문자열, 모든 정수)에 가깝지만, 테이블의 칸 수 m은 유한하다. 서로 다른 키가 m+1개만 들어와도 최소 두 개는 반드시 같은 칸을 공유해야 한다 — 이것이 충돌(Collision)이다.

더 알아보기 · 생일 역설

충돌은 생각보다 훨씬 빨리 일어난다. 1년 366일(=366칸짜리 테이블)에 사람을 무작위로 23명만 모아도, 그중 두 사람의 생일이 같을 확률은 50%를 넘는다. 테이블이 6%(23/366)도 안 찼는데 벌써 충돌이 일어난다는 뜻이다 — 해시 테이블도 마찬가지로, 절반도 채우기 전부터 충돌을 각오해야 한다.

충돌 해결 기법 ① 체이닝(Separate Chaining)

같은 칸에 배정된 키들을 포기하지 않고, 그 칸에 여러 개를 순서대로 이어서 보관하는 방식이다. "체이닝"이라는 이름과 흔히 그려지는 [data | next] 그림 때문에 진짜 연결 리스트(Node + next 포인터)를 쓴다고 생각하기 쉽지만, 실제로는 언어·구현체마다 다르다. Java의 HashMap은 정말로 연결 리스트를 쓰고(체인이 8개를 넘으면 그 칸만 트리로 바꾼다), 반면 파이썬에서 체이닝을 직접 구현할 때는 뒤에서 만들어볼 ChainingHashTable처럼 보통 그냥 list(동적 배열)를 쓴다 — 적재율을 낮게 유지하는 한 한 칸에 몰리는 항목은 보통 1~2개뿐이라, 짧은 리스트를 훑는 것과 짧은 연결 리스트를 따라가는 것 사이에 실질적 차이가 거의 없고, 파이썬의 list가 C로 최적화되어 있어 오히려 더 빠른 경우가 많기 때문이다. 칸이 무엇을 가리키든(연결 리스트의 머리든, 배열이든) 충돌한 키는 그 목록의 끝에 새로 추가된다.

평균 탐색 시간은 O(1 + α)다(α는 적재율, 아래에서 다룬다). 칸마다 매달린 체인이 짧게 유지되는 한 사실상 O(1)에 가깝다. 장점은 테이블이 꽉 차도(α > 1이어도) 계속 넣을 수 있다는 것이다. 단점은 진짜 연결 리스트로 구현했을 경우(Java처럼) 두드러진다 — 참조(포인터)를 위한 메모리가 추가로 필요하고, 노드들이 메모리 여기저기 흩어져 있어 캐시 효율이 떨어진다. 그래서 파이썬처럼 짧은 체인을 배열 기반 list로 구현하는 경우에는 이 단점이 크게 줄어든다.

충돌 해결 기법 ② 개방 주소법(Open Addressing)

체인을 매달지 않고, 배열 안에서만 해결한다. 충돌이 나면 정해진 규칙(탐사 함수)에 따라 다음 빈 칸을 찾아 그곳에 저장한다.

탐사 방식공식특징
선형 탐사
Linear Probing		h_i(k) = (h(k) + i) mod m바로 다음 칸부터 순서대로 확인. 구현이 가장 쉽지만 채워진 칸들이 길게 뭉치는 1차 군집화(Primary Clustering)가 생긴다.
제곱 탐사
Quadratic Probing		h_i(k) = (h(k) + i²) mod m1, 4, 9, … 칸씩 건너뛰며 확인해 군집화를 완화한다.
이중 해싱
Double Hashing		h_i(k) = (h1(k) + i·h2(k)) mod m두 번째 해시 함수로 건너뛰는 간격 자체를 키마다 다르게 만들어, 실전에서 가장 고른 분포를 보인다.

삭제가 까다롭다는 점도 기억해야 한다. 칸을 그냥 비워버리면(None) 그 칸을 건너뛰고 저장됐던 뒤쪽 키를 탐사로 다시 찾지 못하게 될 수 있다. 그래서 실제로는 "삭제됨" 표시(Tombstone)를 남겨, 탐사는 계속 통과시키되 새 삽입만 그 자리를 재사용하게 한다. 평균 탐색 시간은 O(1/(1−α))에 가깝지만, α가 1에 가까워질수록 체이닝보다 훨씬 급격하게 느려진다.

직접 구현해보기 — 기본 해시 함수, 체이닝, 개방 주소법

지금까지 배운 두 가지 충돌 해결 방식을 실제로 동작하는 파이썬 코드로 옮겨보자. 먼저 놀이터에서 쓴 것과 같은 기본 해시 함수부터 정의한다.

def simple_hash(key, m):
    total = sum(ord(ch) for ch in str(key))  # 문자 코드 합
    return total % m                        # 나눗셈법

단 get(key, 기본값)은 던더로 바꾸지 않고 그대로 남겨둔다. 진짜 dict도 d[key](없으면 KeyError)와 d.get(key, 기본값)(없으면 예외 대신 기본값 반환)을 둘 다 따로 제공하기 때문이다 — __getitem__으로 대괄호 문법을 얻고, get()은 안전한 조회용으로 별도로 남겨두는 것이 진짜 dict와 가장 가깝다.

체이닝 — 각 칸을 파이썬 리스트로 두고, 충돌한 키·값 쌍을 그 리스트 끝에 계속 추가한다. 삭제도 리스트에서 빼기만 하면 되므로 단순하다. 여기에 앞서 확인한 CPython dict의 정책과 똑같은 리사이징도 추가한다 — 적재율이 2/3을 넘으면 자동으로 확장한다.

LOAD_FACTOR_LIMIT = 2 / 3  # 적재율이 이 값을 넘으면 확장한다 (CPython 실제 dict와 같은 기준)

class ChainingHashTable:
    def __init__(self, size=7):
        self.size = size
        self.buckets = [[] for _ in range(size)]   # 칸마다 리스트 하나(연결 리스트 역할)
        self._count = 0

    def _hash(self, key):
        return simple_hash(key, self.size)

    def _resize(self):
        old_buckets = self.buckets
        growth = 2 if self._count > 50_000 else 4   # 작을 때 4배, 5만 개 넘으면 2배
        self.size *= growth
        self.buckets = [[] for _ in range(self.size)]
        self._count = 0
        for bucket in old_buckets:
            for key, value in bucket:
                self[key] = value    # __setitem__ 재사용 → 새 테이블 크기로 다시 해시(Rehashing)

    def __setitem__(self, key, value):        # ht[key] = value
        idx = self._hash(key)
        bucket = self.buckets[idx]
        for i, (k, v) in enumerate(bucket):
            if k == key:               # 이미 있는 키면 값만 갱신
                bucket[i] = (key, value)
                return
        bucket.append((key, value))    # 새 키면 체인 끝에 추가
        self._count += 1
        if self._count / self.size >= LOAD_FACTOR_LIMIT:
            self._resize()             # 적재율 초과 → 확장 + 재배치

    def __getitem__(self, key):        # ht[key]
        idx = self._hash(key)
        for k, v in self.buckets[idx]:
            if k == key:
                return v
        raise KeyError(key)

    def __delitem__(self, key):        # del ht[key]
        idx = self._hash(key)
        bucket = self.buckets[idx]
        for i, (k, v) in enumerate(bucket):
            if k == key:
                del bucket[i]
                self._count -= 1
                return
        raise KeyError(key)

    def __contains__(self, key):       # key in ht
        idx = self._hash(key)
        return any(k == key for k, v in self.buckets[idx])

    def __len__(self):               # len(ht)
        return self._count

    def __iter__(self):              # for key in ht
        for bucket in self.buckets:
            for k, v in bucket:
                yield k

    def __repr__(self):
        items = ", ".join(f"{k!r}: {self[k]!r}" for k in self)
        return "{" + items + "}"

    def get(self, key, default=None):    # dict.get()과 똑같은 안전한 조회
        return self[key] if key in self else default


ht = ChainingHashTable(size=7)
ht["cherry"] = 3000
ht["grape"] = 4000    # h("grape")도 2 → "cherry"와 같은 칸, 체인으로 이어짐
print(ht["cherry"])         # 3000
print("grape" in ht)       # True
del ht["cherry"]
print("cherry" in ht)      # False
print(len(ht))              # 1
print(ht)                   # {'grape': 4000}
print(ht.get("없는키", "기본값"))  # 예외 대신 기본값

ht2 = ChainingHashTable(size=7)
for fruit in ["apple", "banana", "cherry", "date", "fig"]:

개방 주소법(선형 탐사) — 배열 두 개(keys, values)만으로 구현한다. 빈 칸은 _EMPTY, 삭제된 칸은 _DELETED라는 전용 표식(sentinel)으로 구분해, 삭제 후에도 탐사가 끊기지 않게 한다.

_EMPTY = object()      # 빈 칸 표시
_DELETED = object()    # 삭제됨 표시 (Tombstone)

class OpenAddressingHashTable:
    def __init__(self, size=7):
        self.size = size
        self.keys = [_EMPTY] * size
        self.values = [None] * size
        self._count = 0

    def _hash(self, key):
        return simple_hash(key, self.size)

    def _find_slot(self, key):
        """key가 있으면 그 위치, 없으면 넣을 수 있는 첫 빈 자리를 찾는다."""
        idx = self._hash(key)
        first_deleted = None
        for i in range(self.size):
            probe = (idx + i) % self.size
            slot = self.keys[probe]
            if slot is _EMPTY:
                return probe, False
            if slot is _DELETED:
                if first_deleted is None:
                    first_deleted = probe        # 지나가면서 tombstone 자리를 재활용
                continue
            if slot == key:
                return probe, True
        return first_deleted, False

    def _resize(self):
        old_keys, old_values = self.keys, self.values
        growth = 2 if self._count > 50_000 else 4   # 작을 때 4배, 5만 개 넘으면 2배
        self.size *= growth
        self.keys = [_EMPTY] * self.size
        self.values = [None] * self.size
        self._count = 0
        for k, v in zip(old_keys, old_values):
            if k is not _EMPTY and k is not _DELETED:
                self[k] = v    # 새 테이블 크기로 다시 해시 — tombstone은 자연히 같이 청소된다

    def __setitem__(self, key, value):        # ht[key] = value
        if key not in self and (self._count + 1) / self.size >= LOAD_FACTOR_LIMIT:
            self._resize()              # 새 키를 넣기 전에 적재율부터 확인
        probe, found = self._find_slot(key)
        if probe is None:
            raise RuntimeError("테이블이 가득 찼습니다 — 리해싱이 필요합니다")
        if not found:
            self._count += 1
        self.keys[probe] = key
        self.values[probe] = value

    def __getitem__(self, key):        # ht[key]
        idx = self._hash(key)
        for i in range(self.size):
            probe = (idx + i) % self.size
            slot = self.keys[probe]
            if slot is _EMPTY:
                raise KeyError(key)             # 빈 칸을 만나면 더 찾을 필요 없음
            if slot == key:
                return self.values[probe]
        raise KeyError(key)

    def __delitem__(self, key):        # del ht[key]
        idx = self._hash(key)
        for i in range(self.size):
            probe = (idx + i) % self.size
            slot = self.keys[probe]
            if slot is _EMPTY:
                raise KeyError(key)
            if slot == key:
                self.keys[probe] = _DELETED        # EMPTY가 아니라 DELETED로 표시!
                self.values[probe] = None
                self._count -= 1
                return
        raise KeyError(key)

    def __contains__(self, key):       # key in ht
        try:
            self[key]
            return True
        except KeyError:
            return False

    def __len__(self):               # len(ht)
        return self._count

    def __iter__(self):              # for key in ht
        for k in self.keys:
            if k is not _EMPTY and k is not _DELETED:
                yield k

    def __repr__(self):
        items = ", ".join(f"{k!r}: {self[k]!r}" for k in self)
        return "{" + items + "}"

    def get(self, key, default=None):    # dict.get()과 똑같은 안전한 조회
        return self[key] if key in self else default


oht = OpenAddressingHashTable(size=7)
oht["cherry"] = 3000   # h("cherry") = 2 → 2번 칸
oht["grape"] = 4000    # h("grape") = 2, 충돌! → 탐사해서 3번 칸에 저장
print(oht["grape"])       # 4000

del oht["cherry"]         # 2번 칸을 EMPTY가 아니라 DELETED로 표시
print(oht["grape"])       # 4000 — tombstone 덕분에 그대로 찾아진다
print("cherry" in oht)     # False
print(len(oht))               # 1

oht2 = OpenAddressingHashTable(size=7)
for fruit in ["apple", "banana", "cherry", "date", "fig"]:
    oht2[fruit] = len(fruit)
print(oht2.size)         # 28 — 체이닝과 똑같이 "fig"에서 적재율 초과 → 4배 확장
print(len(oht2))           # 5 — 확장 후에도 다섯 개 모두 안전하게 재배치됨
print(oht2["apple"])      # 5 — 재배치됐어도 정상 조회

두 구현 모두 _hash를 놀이터와 같은 simple_hash로 두었다 — "cherry"와 "grape"를 직접 놀이터에 넣어보면 똑같은 충돌·탐사 과정이 화면에서 재현되는 것을 확인할 수 있다. 그리고 이제 ht["cherry"]처럼 진짜 dict와 똑같은 문법으로 쓸 수 있게 됐다는 것 자체가, "파이썬 dict는 결국 이런 해시 테이블이다"라는 이론 내용의 실체다.

적재율(Load Factor)과 동적 크기 조정

적재율 α = n / m (n: 저장된 원소 수, m: 테이블 크기)은 테이블이 얼마나 "붐비는지"를 나타내는 값이다. α가 커질수록 체이닝은 체인 길이가 길어지고, 개방 주소법은 탐사 횟수가 급증해 α가 1에 가까워지면 사실상 O(N)에 가까워진다.

해결책은 리사이징(Resizing)/리해싱(Rehashing)이다. 적재율이 일정 임계값(예: 0.75)을 넘으면, 2주차에서 배운 동적 배열의 재할당과 똑같은 방식으로 더 큰 테이블을 새로 만들고 기존의 모든 키-값 쌍을 새 테이블에 다시 해시해서 옮긴다. 이 과정 자체는 O(N)이지만 드물게만 일어나므로, 삽입의 평균(분할상환) 복잡도는 여전히 O(1)로 유지된다 — 2주차의 append 분석과 완전히 같은 논리다.

파이썬 dict의 실제 구현과 Hashable 규칙

흥미롭게도 CPython의 dict·set은 체이닝이 아니라 개방 주소법(의사난수 탐사)으로 구현되어 있다. 3.6 버전부터는 입력 순서까지 보존하도록 내부 구조가 개선되었다.

dict의 키(또는 set의 원소)는 반드시 불변(hashable) 객체여야 한다. list는 내용이 바뀔 수 있어 해시값이 고정되지 않으므로 키로 쓸 수 없고, 대신 tuple을 쓴다. 해시값이 같다고 무조건 같은 키인 것도 아니다 — 파이썬은 해시값이 같은 두 키를 만나면 __eq__로 실제 동등성까지 다시 확인한다(이것도 넓은 의미의 충돌 처리다).

타입별로 해시값은 실제로 이렇게 계산된다

hash()가 구체적으로 어떤 값을 내놓는지는 타입마다 계산 방식이 다르다. 모두가 반드시 지키는 규칙은 단 하나뿐이다 — a == b이면 반드시 hash(a) == hash(b)다(역은 성립하지 않아도 된다. 그게 바로 충돌이다).

  • inthash(n)은 거의 n 그대로다. 아주 큰 정수는 소수 2⁶¹−1로 나눈 나머지로 줄인다. -1은 C 코드에서 오류를 뜻하는 예약값이라 hash(-1)은 대신 -2로 바뀐다.
  • float정수와 값이 같으면 해시도 같아야 하므로(hash(2.0) == hash(2)) 가수·지수를 정수와 같은 방식으로 축소해 계산한다.
  • str · bytesSipHash라는 암호학적 해시 함수를 쓴다. 프로세스마다 무작위로 다른 128비트 키를 붙여 계산하므로, 같은 코드를 실행해도 hash("abc") 값은 실행할 때마다 달라진다.
  • tuple원소들의 해시를 순서를 반영해서 결합한다 — hash((1,2)) != hash((2,1))이 되도록 설계되어 있다.
  • frozenset원소들의 해시를 순서와 무관하게 XOR 기반으로 결합한다. {1,2}와 {2,1}은 같은 집합이므로 해시도 같아야 하기 때문 — 튜플과 정반대 설계다.
  • 사용자 정의 객체__hash__를 따로 정의하지 않으면 id(obj)(메모리 주소) 기반으로 계산한다. __eq__만 재정의하고 __hash__를 그대로 두면 이 규약이 깨질 수 있어, 파이썬이 그 클래스를 자동으로 unhashable로 만들어버린다.
class Point:
    def __init__(self, x, y):
        self.x, self.y = x, y
    def __eq__(self, other):
        return (self.x, self.y) == (other.x, other.y)
    def __hash__(self):
        return hash((self.x, self.y))  # 튜플의 해시 계산 방식을 그대로 재사용

hash(key)가 계산되어도 dict가 그 값을 그대로 인덱스로 쓰는 것은 아니다. 테이블 크기에 맞춰 하위 비트만 남겨(나눗셈법과 사실상 같은 개념) 슬롯을 정하고, 충돌이 나면 CPython 고유의 의사난수 탐사(perturbation을 섞은 개방 주소법)로 다음 자리를 찾는다 — 위에서 배운 선형 탐사보다 한 단계 더 정교한 버전이다.

더 알아보기 · 해시 시드 무작위화

파이썬은 보안을 위해 문자열·바이트의 해시값을 실행할 때마다 무작위로 다르게 만든다(hash randomization). 그래서 같은 코드를 실행해도 hash("abc")의 실제 값은 매번 달라질 수 있다 — 공격자가 해시값을 미리 예측해 일부러 충돌만 일으키는 서비스 거부 공격(Hash DoS)을 막기 위한 장치다.

더 알아보기 · SipHash — 문자열 해시의 실제 알고리즘

SipHash는 2012년 Jean-Philippe Aumasson과 Daniel J. Bernstein이 만들었다. 계기가 바로 2011년 Hash DoS 사태다 — 해시 함수 자체를 비밀 키로 무작위화해 공격자가 충돌을 미리 계산하지 못하게 만드는 실전용 알고리즘으로 설계됐다. 이후 파이썬(PEP 456), 루비, Rust, Redis, 리눅스 커널 등 수많은 시스템이 채택했다.

SipHash는 SHA-256 같은 일반 암호화 해시와 목적이 다르다 — "키를 모르는 사람은 출력을 예측·조작할 수 없어야 한다"가 목표인 키드 유사난수 함수(keyed PRF)라서, 짧은 문자열 키에서도 아주 빠르게 계산되도록 설계됐다. 128비트 비밀 키와 4개의 64비트 내부 상태(총 256비트)를 가지고, 입력을 8바이트씩 블록으로 잘라 밀어 넣으면서 덧셈·비트회전·XOR(ARX 연산)만으로 이루어진 라운드 함수를 반복 적용해 상태를 휘젓는다. 곱셈이나 룩업 테이블이 없어 CPU에서 매우 빠르다.

이름은 SipHash-c-d 형식을 쓴다 — c는 블록마다 도는 압축 라운드 수, d는 마지막에 도는 마무리 라운드 수다. 표준은 SipHash-2-4고, 파이썬은 3.11부터 더 빠른 SipHash-1-3을 기본값으로 쓴다. 128비트 키를 모르면 경우의 수 2128개를 다 시도해야 하므로 공격자가 무차별 대입으로 키를 알아내는 것은 사실상 불가능하다 — 이 키는 프로세스가 시작될 때 OS의 안전한 난수 생성기로 딱 한 번 만들어져 그 프로세스가 끝날 때까지 고정된다(PYTHONHASHSEED로 강제 고정도 가능하다).

더 알아보기 · Hash DoS — 해시 충돌 서비스 거부 공격

해시 함수가 공개되어 있고 결정적이면, 공격자는 서버에 접속하지 않고도 "전부 같은 버킷에 떨어지는 키" 수만 개를 자기 컴퓨터에서 미리 계산해둘 수 있다. 그런 키들로 채운 요청 하나를 보내면, 체이닝 방식에서는 삽입 비용이 1+2+...+N ≈ O(N²)까지 치솟는다. 공격자는 요청 하나(수백 KB)만 보내면 되지만, 서버는 CPU 코어 하나를 몇 초에서 몇 시간까지 묶이게 된다 — 비용이 극도로 비대칭적인 공격이다.

2011년 28C3(카오스 컴퓨터 클럽 컨퍼런스)에서 Klink와 Wälde가 이 공격이 PHP·ASP.NET·Java·Python·Ruby 등 대부분의 웹 플랫폼에서 실제로 통한다는 것을 공개 시연했다 — PHP 5는 파라미터 65,536개짜리 요청 하나로 서버 코어를 약 30초간 묶어둘 수 있었다. 이 개념 자체는 2003년 Crosby·Wallach의 논문에서 이미 경고됐던 것으로, Perl은 그때(5.8.1)부터 해시에 무작위 시드를 섞어 대응해왔다.

지금의 표준 대응은 무작위 비밀 키를 섞는 SipHash 같은 키드(keyed) 해시 함수다(파이썬이 쓰는 방식). Java의 HashMap은 여기에 더해 한 버킷의 체인이 너무 길어지면 그 버킷만 트리로 바꿔, 설령 공격을 당해도 최악의 경우를 O(log N)에 묶어두는 이중 방어까지 둔다.

심화 · Universal Hashing

왜 "무작위" 해시 함수가 필요한가

지금까지 본 해시 함수는 전부 고정되어 있었다 — 한 번 h(key) = ... 식을 정하면 프로그램이 실행되는 내내 똑같은 식을 쓴다. 문제는 이 식이 공개되어 있거나 예측 가능하면, 방금 본 Hash DoS처럼 공격자가 그 식에 딱 맞춰 전부 충돌하는 키들을 미리 계산해둘 수 있다는 것이다. 유니버설 해싱(Universal Hashing)은 이 문제를 근본적으로 없앤다 — 하나의 고정된 함수를 쓰는 대신, 프로그램을 실행할 때마다 잘 설계된 함수 집합(family) H에서 함수를 하나 무작위로 뽑아 쓴다. 공격자는 어떤 키를 넣을지는 정할 수 있어도 실행 중에 어떤 함수가 뽑힐지는 알 수 없으므로, 특정 키 집합이 항상 충돌하도록 미리 설계하는 것 자체가 불가능해진다.

정의

함수 집합 H = {h : U → {0, ..., m−1}}가 유니버설하다는 것은, 서로 다른 두 키 x, y에 대해 H에서 함수를 무작위로 균등하게 하나 뽑았을 때 그 둘이 충돌할 확률이 1/m 이하라는 뜻이다.

Prh∈H [ h(x) = h(y) ] ≤ 1/m서로 다른 모든 키 x ≠ y에 대해 성립

이 조건은 아주 강력하다 — 어떤 특정한 키 집합에 대해서도(공격자가 최악의 경우를 노리고 골랐더라도) 그 안의 두 키가 충돌할 확률이 "완전히 무작위로 배치했을 때"와 같은 수준(1/m)으로 보장된다. "최악의 입력"이라는 개념 자체가 사라지고, 어떤 입력에 대해서도 평균적으로 O(1)이 보장되는 것이다.

구성 방법 — Carter·Wegman 해시 함수족

이런 성질을 만족하는 함수 집합을 만드는 가장 널리 쓰이는 방법은 Carter와 Wegman이 1979년 제안한 구성이다. 우리가 만들 해시 테이블의 크기(칸 수)를 m이라 하고, 키의 전체 범위보다 큰 소수 p를 하나 고정한다. 그리고 프로그램을 실행할 때마다 a ∈ {1, ..., p−1}, b ∈ {0, ..., p−1}을 무작위로 뽑아 다음 함수를 만든다.

ha,b(k) = ((a·k + b) mod p) mod m

앞의 mod p만으로는 결과가 {0, ..., p−1} 범위(아주 큰 값)에 남기 때문에, 실제 테이블 칸 번호로 쓸 수 있도록 mod m으로 한 번 더 줄여준다 — 나눗셈법 h(k) = k mod m과 똑같은 마무리 단계다.

a는 키에 곱해지므로 0이면 키가 통째로 사라져 모든 키가 항상 충돌해버린다(그래서 반드시 제외). b는 단순히 더해지는 값이라 0이어도 문제없다 — a의 범위만 1부터 시작하는 이유다.

a, b를 뽑는 조합의 수만큼 서로 다른 함수가 존재하고(총 (p−1)·p개), 이 함수들의 집합 전체가 유니버설하다는 것이 증명되어 있다. 프로그램을 시작할 때 a, b를 딱 한 번 무작위로 뽑아 고정해두면, 그 실행 동안에는 이 하나의 ha,b를 해시 함수로 계속 쓴다 — 파이썬이 프로세스마다 무작위 시드를 뽑아 SipHash의 키로 쓰는 것과 똑같은 발상이다.

왜 통하는가(직관) — p가 소수이기 때문에, 서로 다른 두 키 x ≠ y를 (a·x+b) mod p와 (a·y+b) mod p라는 두 값으로 보내는 과정은 a, b가 무작위로 뽑히는 한 항상 일대일 대응이 되며, 그 결과값 쌍도 고르게 퍼진다. 이 두 값을 다시 mod m으로 줄였을 때 같은 값이 나올 확률은, 두 값이 각각 무작위로 뽑힌 것이나 마찬가지이므로 정확히 1/m 근처가 된다.

파이썬으로 구현하기

핵심은 인스턴스를 만들 때 딱 한 번 a, b를 무작위로 뽑아 고정한다는 것이다 — 키마다 다시 뽑는 것이 아니다. 문자열 키는 다항식 방식으로 정수로 바꾼 뒤 같은 공식을 적용한다.

import random

class UniversalHash:
    """프로그램(인스턴스)을 새로 만들 때마다 무작위로 해시 함수를 하나 고정한다."""
    _P = (1 << 61) - 1  # 2^61 - 1, 메르센 소수

    def __init__(self, m):
        self.m = m
        self.a = random.randint(1, self._P - 1)   # a != 0
        self.b = random.randint(0, self._P - 1)

    def _to_int(self, key):
        if isinstance(key, int):
            return key % self._P
        n = 0
        for ch in str(key):          # 문자열 → 정수 (다항식 방식)
            n = (n * 131 + ord(ch)) % self._P
        return n

    def __call__(self, key):
        k = self._to_int(key)
        return ((self.a * k + self.b) % self._P) % self.m


h = UniversalHash(m=7)
print(h("apple"), h("banana"), h("cherry"))
# 프로그램을 다시 실행하면 a, b가 새로 뽑히므로
# 같은 키라도 실행마다 다른 인덱스가 나온다.

파이썬의 실제 dict가 이 Carter–Wegman 구성을 그대로 쓰는 것은 아니다 — 대신 SipHash라는, 키를 비밀로 유지하면서 암호학적으로 더 강한 안전성까지 보장하는 함수를 쓴다. 하지만 발상의 뿌리는 같다 — 해시 함수 자체를 실행마다 무작위로 정해서 공격자가 미리 충돌을 계산해둘 수 없게 만드는 것이다. 유니버설 해싱은 이 발상이 왜 수학적으로 통하는지를 최초로 정식화한 이론이고, SipHash는 그 발상을 실전에서 빠르고 안전하게 구현한 결과물이라고 볼 수 있다.

06 실전에서는 이렇게 쓴다

해시 테이블은 이론으로만 존재하는 구조가 아니다. 지금 이 순간에도 다음과 같은 곳에서 쉬지 않고 동작하고 있다.

연락처 주소록

이름을 키로 전화번호를 즉시 조회한다. 배열이면 이름을 찾는 데 O(N)이지만, dict라면 이름 하나로 O(1)에 번호를 꺼낸다.

회원가입 중복 확인

이미 가입된 이메일을 set에 저장해두면, 새로 입력된 이메일이 그 안에 있는지 O(1)로 즉시 확인할 수 있다. 배열이면 전수 비교가 필요하다.

애너그램 판별·그룹화

문자를 정렬한 결과를 키로 써서 defaultdict(list)에 모으면, 철자만 다른 단어들을 한 번의 순회(O(N))로 그룹 지을 수 있다.

Two Sum(두 수의 합)

코딩 테스트 단골 문제. "지금까지 본 값"을 dict에 저장해두면, 목표값에서 뺀 값이 이미 등장했는지 O(1)로 확인해 전체를 O(N)에 푼다.

LRU 캐시

dict(키 → 노드 위치)와 이중 연결 리스트(4주차)를 결합하면 접근·삽입·삭제를 모두 O(1)에 해낼 수 있다. 브라우저 캐시, DB 쿼리 캐시가 실제로 이렇게 동작한다.

심볼 테이블 · DB 인덱스

컴파일러는 변수 이름을, 데이터베이스는 검색 컬럼 값을 해시 기반 구조로 관리해 원하는 위치를 즉시 찾아낸다.

응용 문제 ② — Two Sum(두 수의 합)

def two_sum(nums, target):
    seen = {}                        # 값 → 인덱스
    for i, n in enumerate(nums):
        need = target - n
        if need in seen:
            return [, i]  # 정답 인덱스를 O(1)로 꺼낸다
        seen[n] = i
    return None
① seen[need] — 배열을 이중 for문으로 다 비교하면 O(N²)이지만, "지금까지 등장한 값 → 인덱스"를 dict에 저장해두면 매 반복마다 need in seen과 seen[need]를 각각 O(1)로 확인·조회할 수 있어 전체를 O(N)에 해결한다.

import random

class UniversalHash:
    _P = (1 << 61) - 1

    def __init__(self, m):
        self.m = m
        self.a = random.randint(1, self._P - 1)
        self.b = random.randint(0, self._P - 1)

    def __call__(self, k):
        return ((self.a * k + self.b) % self._P)  self.m   # 실제 테이블 칸 번호로 한 번 더 줄인다

  • 체이닝과 개방 주소법(선형·제곱 탐사, 이중 해싱)의 차이를 비교할 수 있다.
  • 적재율과 리해싱이 동적 배열의 재할당과 어떻게 연결되는지 설명할 수 있다.
  • unhashable type 에러가 나는 이유와 회피 방법(튜플 사용)을 설명할 수 있다.
  • Counter, defaultdict를 활용해 빈도수 집계 코드를 작성할 수 있다.
  • dict를 활용해 O(N²) 문제를 O(N)으로 최적화하는 코드를 스스로 작성할 수 있다(예: Two Sum).
